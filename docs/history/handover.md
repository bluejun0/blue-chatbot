**클론 대상:** 와이즈에이아이 AiU 홈페이지 챗봇 (`ai.wiseai.co.kr`)
**작성:** 2026-09-16 / 블루소프트 준영
**상태:** 구현 미착수

## 표기 규칙

| 표기 | 뜻 |
|---|---|
| **[관찰]** | 벤치마크를 직접 열어 확인한 사실 |

## 0. 이 챗봇의 목적

**방문자를 문의(리드)로 전환하는 것.** FAQ 응답은 목적이 아니라 대화를 시작시키는 수단이다.

근거 **[관찰]** — 와이즈에이아이의 `/inquiry` 페이지에는 **문의 입력 폼이 없다.** 도입절차 4단계 안내, 도입 FAQ 목록, 그리고 "기능·가격·도입 프로세스 등 궁금한 사항을 남겨주시면 담당자가 배정되어 빠르게 연락드립니다"라는 안내문과 챗봇 유도만 있다. 입력 필드는 FAQ 검색창 하나뿐이다.

즉 **폼을 챗봇으로 대체했다.**

> 정정: 이전 메모에서 "폼은 그대로 유지되고 챗봇은 추가 유입구"라고 적었으나 사실과 다르다. 폼이 없어졌다.

## 1. 시스템 구성 **[관찰]**

```
홈페이지 (Next.js)
  └ embed.js 한 줄
      └ <iframe id="chat-embed-widget-frame"
                src="oms.aiu-ai.co.kr/embed/chat?company=wiseai&api_key=...">

챗봇 서비스 (oms.aiu-ai.co.kr, 별도 도메인)
  ├ GET  /svc/settings/embed/config?api_key=...   위젯 설정
  ├ POST /langgraph/threads                        대화 스레드 생성
  └ POST /langgraph/threads/{id}/runs/stream       응답 스트리밍
```

- `company` + `api_key` 쌍으로 구분되는 **멀티테넌트**
- 런타임은 **LangGraph Server** 셀프호스팅
- 홈페이지 쪽 코드는 스크립트 한 줄이 전부

## 2. 기능 명세

### F-1. 위젯 진입

| 항목 | 내용 |
|---|---|
| 진입점 | 우하단 플로팅 버블 **[관찰]** |
| 툴팁 | "WiseAI AgentX / AI를 통해 무엇이든 물어보세요!" **[관찰]** |
| 헤더 | 라벨 텍스트, 테마 변경(라이트/다크) 버튼, 닫기 버튼 **[관찰]** |
| 입력창 | placeholder "메시지를 입력하세요...", 전송 버튼 **[관찰]** |
| 노출 페이지 | 전 페이지 공통 **[관찰]** |

### F-2. 온보딩 — 인사말 + 제안 액션

위젯을 열면 자유 입력창이 아니라 **인사말 한 문단 + 카드 목록**이 먼저 나온다. 입력창은 아래에 있지만 시선은 카드로 간다. **[관찰]**

설정 API가 내려주는 실제 구조 **[관찰]**:

```json
{
  "label": "챗봇",
  "greeting_message": "안녕하세요. 와이즈에이아이 AI 상담원입니다. 서비스 도입 문의, 서비스 정보 안내, 사업 제휴, 기존 고객 지원 등 다양한 문의를 빠르게 도와드리고 있습니다. 무엇을 도와드릴까요?",
  "suggested_actions": [
    {
      "id": "o96mumm",
      "title": "서비스 정보 안내",
      "description": "기능·절차·정책 등 문서와 FAQ 기반 안내",
      "icon": "search",
      "message": "서비스 정보를 안내받고 싶어"
    },
    {
      "id": "se5eh2l",
      "title": "에이유 도입문의",
      "description": "병원용 에이유 도입 상담·견적 접수",
      "icon": "stethoscope",
      "message": "에이유 도입문의를 하고싶어"
    },
    {
      "id": "tf7xlfm",
      "title": "일반기업용 도입문의",
      "description": "일반기업용 AI 솔루션 서비스 관련 문의",
      "icon": "building",
      "message": "일반기업용 도입문의를 하고싶어"
    },
    {
      "id": "lc8i4vc",
      "title": "사업제휴 문의",
      "description": "사업 제휴, 협업, 파트너십, 투자, 제안 등 사업 관련 문의",
      "icon": "document",
      "message": "사업제휴 관련 문의를 하고싶어"
    }
  ]
}
```

핵심 동작: **카드를 누르면 `message` 값이 사용자 발화로 전송된다.** 카드는 UI가 아니라 **미리 써둔 사용자 대사**다. **[관찰 — 클릭하니 "서비스 정보를 안내받고 싶어"가 내 메시지로 찍힘]**

카드 한 장의 구성: `id` / `title`(굵은 제목) / `description`(회색 부제) / `icon` / `message`(전송될 발화).

### F-3. 인텐트 확보

인텐트를 LLM이 분류하지 않고 **사용자에게 카드로 직접 받는다.** 자유 입력도 가능하지만 첫 턴의 기본 경로는 카드다. **[관찰]**

카드 4장이 곧 이 회사의 문의 갈래다 — 정보 안내 / 주력 제품 도입 / 부제품 도입 / 제휴. 인사말에는 "기존 고객 지원"도 언급되나 카드로는 없다. **[관찰]**

### F-4. 정보 안내 (FAQ 응답)

- 카드 설명에 따르면 **"기능·절차·정책 등 문서와 FAQ 기반 안내"** **[관찰]**
- 카드를 누른 직후 바로 답하지 않고 **범위를 좁히는 질문**을 던진다 **[관찰]**
  > "네, 저희 서비스에 대해 궁금하신 점이 있으시군요. 구체적으로 어떤 기능이나 서비스 내용이 궁금하신가요? 알고 싶으신 부분을 말씀해 주시면 바로 확인해서 안내해 드리겠습니다."
- 지식원 규모(공개된 것 기준): **FAQ 19건, 카테고리 6종** — 인바운드 / 아웃바운드 / AI 페이지 / 기타 / 서비스이용 / 결제 **[관찰]**

### F-5. 민감 주제 차단 + 자격 질문 ★ 이 명세의 핵심

요금을 물었을 때의 실제 대화 **[관찰]**:

```
나  : 에이유 요금제랑 도입 비용이 어떻게 되나요?
봇  : 에이유 서비스 도입을 위한 요금과 비용에 대해 문의하셨군요.
      안내를 위해 한 가지만 먼저 여쭤볼게요.
      현재 병원을 운영 중이신 기존 고객님이신가요,
      아니면 신규 도입을 고민 중이신가요?
나  : 신규 도입을 고민 중입니다. 치과입니다.
봇  : 문의하신 요금과 도입 비용 정보는 안내 담당 상담원이
      자세히 도와드리겠습니다. 잠시만 기다려 주세요.
```

읽어낼 수 있는 규칙:

1. **가격은 끝까지 말하지 않는다.** 두 턴을 주고받았지만 숫자는 한 번도 안 나왔다.
2. 대신 **자격 질문(qualification)을 정확히 하나** 던진다 — 기존 고객인가 신규인가.
3. 답을 받는 즉시 **사람에게 넘긴다.**

즉 특정 주제(가격, 견적, 계약)는 **답변 금지 + 인계 트리거**로 지정돼 있다. **[추정]** 봇이 잘못된 가격을 말하면 그게 곧 잘못된 약속이 되므로 합리적인 설계다.

자격 질문의 목적도 분명하다 — 기존 고객이면 지원팀, 신규면 영업팀. **담당자 배정을 위한 최소 정보 한 가지만 챗봇이 받아낸다.** **[추정]**

### F-6. 리드 접수

**관찰하지 못했다.** 인계 시점에서 실제 상담원이 붙어 대화를 중단했다.

**[추정]** 인계 전 또는 대기 중에 연락처를 받을 것으로 보인다. `/inquiry`의 문구 "담당자가 배정되어 빠르게 연락드립니다"가 근거.

**[미정]** 우리가 받을 항목과 순서.

### F-7. 사람 상담원 인계

- 인계 멘트 **[관찰]**: "문의하신 {주제} 정보는 안내 담당 상담원이 자세히 도와드리겠습니다. 잠시만 기다려 주세요."
- 인계 갈래가 카드 단위로 나뉜다 — 병원 도입 / 일반기업 도입 / 제휴는 받는 팀이 서로 다르다 **[추정]**
- 상담원 쪽 화면이 무엇인지는 **확인 불가** (외부에서 보이지 않음)
- 부재 시 처리, 영업시간 밖 처리도 **확인 불가**

### F-8. 관리자 설정

인사말, 카드 목록, 위젯 라벨이 **서버 설정으로 내려온다.** 코드 배포 없이 바꿀 수 있다는 뜻. **[관찰 — config API 응답]**

FAQ 관리 화면, 상담원 배정 설정, 영업시간 설정 등이 있을 것으로 보이나 **확인 불가**. **[추정]**

### F-9. 공개 FAQ 페이지

챗봇과 별개로 `/inquiry`에 FAQ가 웹페이지로도 노출된다. **[관찰]**

- 카테고리 필터 6종 + "전체"
- 질문/답변 전문 검색창
- 페이지네이션 (5건씩, 4페이지, 총 19건)
- 각 항목에 카테고리 배지 표시

챗봇과 같은 FAQ 데이터를 쓰는 것으로 보인다. **[추정]** 사실이라면 FAQ를 한 곳에서 관리해 챗봇과 웹페이지 양쪽에 쓰는 구조다.

## 3. 우리 버전 — 클론 범위

각 기능을 그대로 따라할지, 바꿀지, 뺄지를 정해야 한다. **전부 [미정]이다.**

| # | 기능 | 우리도 필요한가 | 메모 |
|---|---|---|---|
| F-1 | 플로팅 버블 위젯 | | |
| F-2 | 인사말 + 제안 카드 | | 카드 세트를 새로 정해야 함 |
| F-3 | 카드로 인텐트 확보 | | Claude 제안이며 합의 안 됨 |
| F-4 | FAQ 기반 응답 | | FAQ는 이미 만들어둔 것이 있음 |
| F-5 | 민감 주제 차단 + 자격 질문 | | **무엇을 답하지 않을지** 목록이 필요 |
| F-6 | 리드 접수 | | 받을 항목 미정 |

### 블루소프트 특수 사항

와이즈에이아이의 카드 세트를 그대로 못 쓴다. 우리 문의 갈래는 다르다.

특히 **기존 고객 지원**이 다르다. 대학 LMS를 운영 중이라 "우리 학교 로그인이 안 돼요" 같은 문의가 들어올 수 있고, 이건 신규 영업 리드와 처리 경로가 완전히 다르다. 와이즈에이아이도 인사말에는 "기존 고객 지원"을 넣었지만 카드로는 안 뺐다 — 이 갈래를 어떻게 다룰지가 우리 쪽 숙제다. **[미정]**

## 4. 정해진 것과 안 정해진 것

### [결정] 준영이 정한 것

- **FastAPI 단독**, LangChain/LangGraph 미사용
- **사람 상담원 인계 필요**
- **상담원 대기: 업무시간엔 실시간 가능**
- FAQ 선택형 방식 — 미리 정한 FAQ 중 LLM이 하나를 골라 맥락에 맞게 다듬어 제시
- 간단한 FAQ를 이미 작성해둠 (형태·개수 미확인)

### [제안] Claude가 제안만 했고 합의되지 않은 것

아래는 전부 **미결**이다. 문서에 "합의됨"으로 적었던 것을 정정한다.

- 첫 턴 카드 라우팅
- SSE로 방문자 실시간 수신
- 구조화 JSON 한 번으로 인텐트+FAQ+리드 슬롯 처리
- `conversations.status` 상태 모델
- 데이터 모델 전반
- 상담원 콘솔을 슬랙 스레드로 (→ 철회, 미정)
- 부재 시 3분 후 리드 수집 전환
- 작업 순서 4단계

### [미정] 큰 갈림길

**1) 상담원 콘솔**

| 안 | 장점 | 대가 |
|---|---|---|
| 슬랙 스레드 | 콘솔 불필요, 모바일 공짜, 이미 보고 있는 화면 | 슬랙 종속. 고객사에 팔면 그쪽도 슬랙 필요. 내부 메모 유출 위험 |
| 자체 콘솔 | 그대로 팔 수 있는 완결 제품 | 작업량 최대 — 실시간 전송, 로그인, 배정, 읽음 처리, 모바일 |
| 기성 솔루션(채널톡 등) | 가장 빠름. 콘솔·부재중·모바일 앱 이미 있음 | 제품화 포기 |

**2) 임베드형 제품으로 갈 것인가**

와이즈에이아이처럼 별도 서비스 + 스크립트 한 줄 구조로 처음부터 만들면 나중에 고객사에 그대로 팔 수 있다. 홈페이지에 직접 박아 넣으면 나중에 떼어내는 게 일이 된다. 1)과 맞물린 결정이다.

## 5. 기술 메모 (부록)

명세가 정해진 뒤에 참고할 것들. **명세보다 앞서지 않는다.**

### LangGraph를 쓰지 않는 근거

- 툴 호출은 공급자 API의 네이티브 기능이라 루프는 30~50줄
- 상담원 인계 중에는 봇이 아예 돌지 않는다 → 멈췄다 재개할 그래프가 없음
- 팀이 PHP/Moodle 중심이라 레이어를 더 얹으면 인계 비용 증가

**재검토 조건:** 툴 실행 전 사용자 승인이 필요해질 때 / 며칠 걸리는 장기 워크플로 / 상담원 옆에서 도는 코파일럿 / 여러 명이 에이전트를 만들어 공통 런타임이 필요할 때.

### 반드시 넣어야 할 안전장치

**개인정보**
- 연락처를 묻기 직전 수집 항목·목적·보관기간 고지 후 동의. 동의 시각을 리드 레코드에 저장 (문구는 법률 확인 필요)
- 대화 로그와 리드 테이블 분리 또는 로그 쪽 마스킹
- 외부 콘솔(슬랙 등)을 쓰면 그쪽 보존 정책·접근 권한 확인

**인계 사고**
- 상담원 내부 메모가 방문자에게 새지 않게. 상담원 입력이 곧 전달되는 구조라면 접두어 규칙, 자체 콘솔이면 내부 메모 입력란 분리. **어느 쪽이든 반드시 설계에 넣을 것**

**비용·남용**
- 세션당 턴 수 상한, IP별 rate limit, 일일 토큰 상한
- `api_key`가 쿼리스트링에 노출되는 구조 → 서버에서 Origin/Referer 화이트리스트

# 유지보수 요청 검색 설계

## 목표

챗봇이 blue-iWorks 업무현황판의 유지보수 요청을 근거로 답한다. 사용자는 챗봇 한 곳에만
질문하고, 어느 자료를 찾아볼지는 모델이 정한다.

FAQ만으로는 답할 수 없는 질문이 있다. "성적 입력 오류가 전에도 있었나"는 등록된 FAQ에
없지만 요청 이력에는 있다. 이 질문에 답하려면 요청 본문을 검색해야 하고, 요청은 전부
프롬프트에 넣기에 너무 많다.

## 범위

**이번에 만드는 것**

- 유지보수 요청을 주기적으로 읽어 임베딩해 저장하는 색인 작업
- 질문과 가까운 요청을 찾는 검색
- 모델이 검색 여부를 스스로 정하는 도구 사용 구조
- 검색 자료를 하나 더 붙일 때 쓰는 등록 지점
- 임베딩 모델을 바꿔 끼울 수 있는 구조와, 여러 모델을 같은 잣대로 비교하는 스크립트

**이번에 만들지 않는 것**

- FAQ 응답 방식 변경. FAQ는 지금처럼 프롬프트에 전부 싣는다
- 사용자 구분과 권한별 노출 제어
- 발표 주제, 대학 접속정보 검색. 등록 지점만 만들어 두고 실제 추가는 다음 작업이다
- 계정, 비밀번호, 데이터베이스 접속정보가 담긴 자료의 검색
- 건수를 세거나 합치는 집계 질문. 검색 도구는 가까운 것을 몇 건 돌려줄 뿐 세지 않는다
- 모델이 SQL 문장을 만드는 방식. 모델은 정해진 파라미터의 값만 채운다

## 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 검색 대상 | 유지보수 요청 | 건수가 많아 프롬프트에 전부 넣을 수 없다 |
| 벡터 저장소 | MariaDB 12.3 | 이미 쓰는 데이터베이스가 벡터를 지원한다 |
| 임베딩 | OpenAI 임베딩 API로 시작 | 서버에 모델을 올리지 않아도 된다 |
| 임베딩 교체 | 인터페이스 하나 뒤에 두고 설정값으로 바꾼다 | 나중에 직접 구축한 모델로 바꿀 예정이다 |
| 모델 비교 | 같은 질문 세트로 모델별 재현율을 잰다 | 어느 모델이 이 데이터에 맞는지는 재봐야 안다 |
| 응답 방식 | 도구 사용 | 자료가 여럿이라 어디를 볼지 고르는 단계가 필요하다 |
| 검색 조건 | 모델은 정해진 파라미터만 채운다 | SQL은 우리 코드가 만든다. 모델이 쓴 글자가 SQL에 들어가지 않는다 |
| 권한 | 구분하지 않는다 | 사내 인원만 접근하며 민감한 자료는 대상에서 뺀다 |

### 벡터 지원 확인

MariaDB 12.3.3에서 아래가 동작하는 것을 확인했다.

- `VECTOR(n)` 컬럼 형식
- `VECTOR INDEX`
- `VEC_FromText()`, `VEC_DISTANCE_COSINE()`

### 전문검색을 쓰지 않는 이유

MariaDB의 `FULLTEXT`는 한국어에서 쓸 수 없다. 확인한 내용은 다음과 같다.

- `innodb_ft_min_token_size`가 3이라 두 글자 단어가 색인되지 않는다. 성적, 점수, 출석처럼
  업무 요청에서 자주 쓰는 말이 전부 검색되지 않는다
- 조사가 붙으면 다른 단어가 된다. "이화여대"로 찾으면 "이화여대의"가 걸리지 않는다
- `ngram` 파서가 없어 이 문제를 우회할 수 없다

### 기준선

포털에 요청 유사도 검색이 이미 있다. 제목과 본문을 공백으로 잘라 두 글자 이상 토큰을 만들고
IDF 가중 코사인 유사도를 계산한다. 이 방식이 잡지 못하는 것은 셋이다.

- 조사와 어미가 다른 같은 단어
- 다른 말로 쓴 같은 뜻
- 오타

이번 작업은 이 셋에서 더 나은 결과를 내야 의미가 있다.

## 구조

### 검색 자료 등록

검색 자료마다 이름, 설명, 검색 함수를 갖는다. 이름과 설명은 그대로 도구 정의가 된다.

```python
@dataclass(frozen=True)
class Evidence:
    source: str
    id: str
    title: str
    content: str


class SearchSource(Protocol):
    name: str
    description: str

    def search(self, query: str, k: int) -> list[Evidence]: ...
```

등록 목록에서 도구 목록을 만든다.

```python
SOURCES: list[SearchSource] = [RequestSource(engine, embedder)]
```

자료를 하나 더 붙일 때 바꾸는 것은 이 목록 한 줄과 그 자료의 검색 구현, 색인 구현뿐이다.
응답 흐름은 바뀌지 않는다.

### 임베딩

임베딩은 인터페이스 하나 뒤에 둔다. 색인과 검색은 어느 모델을 쓰는지 모른다.

```python
class Embedder(Protocol):
    name: str          # "openai-3-small", "bge-m3", "qwen3-0.6b"
    dimension: int

    def embed(self, texts: list[str]) -> list[list[float]]: ...
```

OpenAI, BGE-M3, Qwen3처럼 모델마다 구현 하나씩이다. 어느 구현을 쓸지는 `EMBEDDING_MODEL`
설정값이 정한다. `name`은 벡터 테이블 이름과 색인 위치의 키에 쓰인다.

### 색인

원본에서 바뀐 것만 읽어 임베딩하고 저장한다. 요청에는 마지막 변경 시각이 있어 전체를 다시
임베딩하지 않는다.

```
원본 요청  --(마지막 색인 시각 이후 변경분)-->  제목과 본문을 임베딩  -->  저장
```

색인 위치는 마지막으로 처리한 변경 시각이다. 자료와 모델의 쌍마다 하나씩 보관한다. 모델을
하나 추가하면 그 모델로 전체를 한 번 색인하고, 그 뒤로는 바뀐 것만 따라간다. 기존 모델의
테이블은 그대로 두므로 운영 중에 새 모델을 병행 색인할 수 있다.

색인 작업은 응답 경로와 분리된 별도 실행이다. 실패해도 챗봇 응답은 계속 동작하며, 그 경우
검색 결과가 최신이 아닐 뿐이다.

### 검색

질문을 임베딩해 코사인 거리로 가까운 것을 고른다. 상태나 보관 여부처럼 값이 정해진 조건은
벡터가 아니라 조건절로 거른다.

모델이 채울 수 있는 파라미터는 아래로 고정한다. 모델은 이 값만 채우고 SQL은 우리 코드가
만든다. 모델이 쓴 글자가 SQL 문장에 들어가는 일은 없다.

| 파라미터 | 형식 | 허용 값 |
|---|---|---|
| `query` | 문자열 | 검색할 문장 |
| `status` | 문자열, 선택 | 요청 상태 목록 중 하나. 목록에 없는 값은 거부한다 |
| `team` | 문자열, 선택 | 개발담당팀 목록 중 하나 |
| `include_archived` | 참거짓 | 기본값은 거짓 |
| `limit` | 정수 | 기본값 5, 상한은 `SEARCH_TOP_K` |

```sql
SELECT request_id, title, body,
       VEC_DISTANCE_COSINE(embedding, VEC_FromText(?)) AS distance
FROM request_vectors__openai_3_small
WHERE archived = 0 AND status = ?
ORDER BY distance
LIMIT ?
```

테이블 이름은 `Embedder.name`에서 온다. 조건절은 파라미터가 채워진 것만 붙는다.

벡터가 잘하는 일과 조건절이 잘하는 일을 나눈다. "비슷한 요청"은 벡터가, "보류 상태인 것"은
조건절이 맡는다. 건수를 세는 질문은 이 도구가 답하지 못한다. 집계 질문을 받으려면 집계
도구를 따로 정해서 붙인다.

### 응답

모델에게 검색 도구를 주고 쓸지 말지 맡긴다. FAQ는 지금처럼 프롬프트에 전부 싣는다.

- FAQ로 답할 수 있는 질문이면 도구를 부르지 않는다
- 요청 이력이 필요하면 도구를 부르고, 결과를 근거로 답한다
- 어느 쪽에도 근거가 없으면 지금과 같은 안내 문구를 돌려준다

도구 호출과 결과 전달은 Anthropic SDK의 도구 실행기가 처리한다. 직접 반복문을 작성하지
않는다. 이 기능은 Python SDK에서 베타이며, 동작이 바뀌면 직접 반복문을 작성하는 방식으로
대체한다.

구조화 출력과 도구 사용은 함께 쓸 수 있다. 최종 응답만 지정한 형식을 따르고, 중간의 도구
호출은 형식 제약을 받지 않는다.

## 데이터 모델

벡터 테이블은 자료와 모델의 쌍마다 하나다. 차원이 모델마다 달라 한 컬럼에 담을 수 없고,
비교하려면 나란히 있어야 한다. 이름은 `{자료}_vectors__{모델 이름}`이다.

```sql
CREATE TABLE request_vectors__openai_3_small (
  request_id     VARCHAR(32)  NOT NULL PRIMARY KEY,
  title          VARCHAR(500) NOT NULL,
  body           MEDIUMTEXT   NULL,
  status         VARCHAR(60)  NOT NULL DEFAULT '',
  team           VARCHAR(60)  NOT NULL DEFAULT '',
  board          VARCHAR(40)  NOT NULL DEFAULT '',
  archived       TINYINT(1)   NOT NULL DEFAULT 0,
  req_date       DATE         NULL,
  source_updated INT UNSIGNED NOT NULL,
  embedded_at    DATETIME     NOT NULL,
  embedding      VECTOR(1536) NOT NULL,   -- 차원은 Embedder.dimension
  VECTOR INDEX (embedding),
  INDEX idx_archived (archived),
  INDEX idx_status (status)
);

CREATE TABLE index_state (
  source     VARCHAR(40)  NOT NULL,
  model      VARCHAR(40)  NOT NULL,
  cursor     INT UNSIGNED NOT NULL DEFAULT 0,
  indexed_at DATETIME     NULL,
  PRIMARY KEY (source, model)
);
```

`index_state`는 자료 이름과 모델 이름을 키로 하므로 자료나 모델이 늘어도 그대로 쓴다.

벡터 차원은 `Embedder.dimension`이 정한다. 새 모델은 새 테이블을 받으므로 기존 테이블을
다시 만들 일은 없다.

저장 용량은 고려 대상이 아니다. 요청 5천 건이면 차원을 1536으로 잡아도 30MB 미만이다.

## 모델 비교

같은 질문 세트를 모델별 테이블에 던져 결과를 나란히 본다.

질문 세트는 실제 요청에서 뽑은 질문 20~50개와, 각 질문에 나와야 하는 요청 id로 이루어진다.
"이 질문이면 이 요청이 나와야 한다"는 손으로 정한다. 특히 기준선이 잡지 못하는 세 가지 — 조사와
어미가 다른 같은 단어, 다른 말로 쓴 같은 뜻, 오타 — 를 질문 세트에 넣는다.

```
모델                재현율@5
openai-3-small      0.84
bge-m3              0.88
qwen3-0.6b          0.80
```

비교 스크립트는 운영 코드가 아니라 별도 도구다. 질문 세트가 한 번 만들어지면 모델을 바꿀
때마다 같은 잣대로 잰다.

## 임베딩 모델 전환 절차

1. 새 모델의 `Embedder` 구현을 작성한다
2. 그 모델의 벡터 테이블을 만들고 전체를 색인한다. 기존 서비스는 계속 동작한다
3. 비교 스크립트로 기존 모델과 나란히 잰다
4. `EMBEDDING_MODEL` 설정을 바꾼다. 검색이 새 테이블을 본다

## 근거 검증

지금은 응답의 `matched_id`가 FAQ 항목의 id에 있는지 확인하고, 없으면 안내 문구로 바꾼다.
자료가 여럿이 되면 id만으로는 어느 자료의 것인지 알 수 없다.

근거를 자료 이름과 id의 쌍으로 바꾼다. 검증은 그 자료가 이번 대화에서 실제로 돌려준
id인지를 확인한다. 모델이 보지 않은 것을 인용할 수 없다.

근거가 없으면 지금과 같은 안내 문구를 돌려준다. 이 동작은 유지한다.

## 설정

| 이름 | 용도 |
|---|---|
| `OPENAI_API_KEY` | 임베딩 호출 인증 |
| `EMBEDDING_MODEL` | 쓸 `Embedder` 구현의 이름. 검색이 볼 벡터 테이블도 이 값으로 정해진다 |
| `SEARCH_TOP_K` | 검색이 돌려주는 최대 건수 |

`OPENAI_API_KEY`는 `SecretStr`로 둔다. 기존 `ANTHROPIC_API_KEY`와 같은 방식이라 로그와
`model_dump()`에 원문이 남지 않는다.

## 오류 처리

| 상황 | 동작 |
|---|---|
| 임베딩 호출 실패 | 도구 결과에 실패를 담아 돌려준다. 모델이 검색 없이 답하거나 안내 문구를 낸다 |
| 검색 결과 없음 | 빈 결과를 돌려준다. 실패가 아니다 |
| 색인 작업 실패 | 색인 위치를 옮기지 않는다. 다음 실행에서 같은 지점부터 다시 시도한다 |
| 원본을 읽을 수 없음 | 색인만 멈춘다. 챗봇 응답은 계속 동작한다 |

임베딩 호출이 실패해도 FAQ 응답은 영향을 받지 않는다.

## 테스트

- 검색 조건절이 보관된 요청을 제외하는지 확인한다
- 색인이 마지막 변경 시각 이후의 것만 처리하는지 확인한다
- 색인이 실패하면 색인 위치가 그대로인지 확인한다
- 검색 결과에 없는 근거를 모델이 인용하면 안내 문구로 바뀌는지 확인한다
- 자료를 하나 더 등록하면 도구 목록에 반영되는지 확인한다

임베딩 API와 데이터베이스 벡터 함수는 우리 코드가 아니므로 동작 자체를 확인하지 않는다.

## 자료를 하나 더 붙이는 절차

1. 그 자료의 `SearchSource` 구현을 작성한다
2. 그 자료의 색인 구현을 작성한다
3. 쓰는 모델마다 벡터 테이블을 추가한다
4. `SOURCES`에 한 줄 추가한다

응답 흐름과 근거 검증은 바꾸지 않는다.

## 아직 정하지 않은 것

- **첫 OpenAI 모델.** `text-embedding-3-small`(1536차원)과 `-large`(3072차원) 중 무엇으로
  시작할지. 차원은 그 선택에 따라온다
- **색인 실행 주기와 실행 방법**
- **원본 요청에 접근하는 경로**
- **응답을 흘려보낼 때 도구 호출 구간을 어떻게 보여줄지.** 도구를 부르는 동안에는 내보낼
  내용이 없어 화면이 멈춘 것처럼 보인다

## 승인이 필요한 것

유지보수 요청의 제목과 본문이 외부 임베딩 API로 전송된다. 대학에서 접수한 내용이 포함되므로
사용료와는 별개로 자료를 외부로 보내는 것에 대한 승인이 필요하다.
